# Use short-lived Issue Branches into main

The Example Project will use one protected `main` branch and short-lived Issue Branches integrated through linked pull requests with automated checks and resolved conversations. Because the example has one real owner and fictional participants cannot approve pull requests, it requires no GitHub approval; live multi-person Fellow teams should require at least one real collaborator's approval. Pull requests use merge commits so the exact reviewed commit named by Workflow Runs and Artifact Manifests remains reachable after its source branch is deleted. Accepted monthly outcomes will be preserved by GitHub milestones and annotated tags/releases, not by `dev` and durable month branches; this reduces coordination overhead, models the workflow recommended to Fellow teams, and removes the former contrived merge-conflict demonstration while the unused pre-created branches still contain no unique work.
